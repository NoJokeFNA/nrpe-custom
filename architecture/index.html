Architecture and maintenance map

Source 9f3fcd5

The host Python controller coordinates Docker Compose. Containers perform the actual package work; target packages are never installed on the development host. The optional terminal UI translates choices into the same CLI arguments used by automation. It does not bypass target locks or artifact validation.

A verify run

build stops before installation testing. test starts from existing artifacts and checks those bytes, without establishing that they match the current source checkout. Targets run sequentially within a command and the first failure stops the remaining targets. Different target runs can proceed independently.

A pass is attached to the artifact's identity and SHA-256, including the SLES user and matching client RPMs. Replacing any invalidates the matching result. Run reports are local records, not cryptographically signed attestations. See the workflow reference for cleanup, stale locks, and report limitations.

Script responsibility review

All existing shell/Python scripts have active callers. The review retained the package-format boundaries and the already-shared TLS protocol test. Shell is used for native package tools; Python is used for structured metadata and narrow source transformations. Download/source preparation uses a modern Python stage; target compilation and installation use native SLES 12 tools without Python.

SLES 12 downloads are prepared separately, then verified and installed with the native RPM implementation before any target code is built. prepare_sles_inputs.py produces only pinned inputs, not target binaries. verify-sles-packages.sh requires exact hash/signature/vendor/version coverage; verify-sles-environment.sh checks the actual 12.3 identity and clean runtime base. The support-package build creates genuine macros/user RPMs; no dependency provides are faked.

Terminal interaction lives in menu.py; workflow execution remains in the controller. Server/companion checksums use one streaming helper in state.py, with the manifest read once per artifact inspection. Native SLES signature and identity verification lives in verify-sles-packages.sh; the unused Python duplicate was removed. The legacy build.py remains a thin compatibility wrapper for existing callers, without its own workflow engine.

Images and updates

Builder images contain compilers and build requirements; runtime images contain only test/runtime prerequisites. A successful fresh-container install therefore cannot rely on a compiler or NRPE server preinstalled by the builder. Keeping two roles is intentional even when both derive from the same distribution base.

Docker caches layers. --pull checks base images, while package-source updates are a different concern: Debian discovers sources through APT at build time; SLES uses explicitly reviewed pinned manifests. The controller does not yet compare a complete remote source/recipe identity to decide whether existing outputs need rebuilding. See repeatability.

Future website structure (deferred)

A component-oriented structure, evaluated from the maintainer's supplied website example, is a useful future direction: shared page layouts, reusable UI partials, separate content collections with validated metadata, and small route definitions. Apply those responsibilities to the existing static renderer before introducing another framework. Keep Markdown as the canonical documentation source, local assets and current link/publication guards.

No framework migration is scheduled by this note. An Astro evaluation would need static output compatible with GitHub Pages, project-base-path support, equivalent Markdown/code/diagram rendering, source and license review, and the same browser and publication checks. The reference's standalone Node server configuration is not a drop-in deployment for this project. Do not copy its unlicensed source or add a server dependency solely to reproduce its directory names.
