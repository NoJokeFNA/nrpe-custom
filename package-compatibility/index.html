NRPE package compatibility matrix

Source 4dc7aaf

Reviewed: 30 October 2026. This is a package/build-feature matrix, not a list of operating systems that universally need a patch. A custom argument-enabled build is relevant only when remote arguments are required and the installed server package lacks compiled argument support. Fixed local commands do not require that feature.

The project changes native packaging options rather than implementing an OS patch. Argument support needs both --enable-command-args at build time and a deliberate runtime policy (dont_blame_nrpe=1). A disabled runtime setting alone does not establish that compilation is missing. Keep Bash command substitution disabled and use reviewed command definitions.

Confirmed packaging and runtime findings

The versions below identify inspected or recorded examples, not a promise that they are the latest packages in every repository. Evidence is either a source review or the explicitly listed container argument probe; neither establishes production TLS or host lifecycle behavior. The dated follow-up records the method, versions, scope and corrected FreeBSD interpretation. Only the targets marked supported are implemented by this tool.

For Debian, recorded versions come from the published package evidence. The builder discovers the actual source from the selected suite; this matrix does not pin a future build to those examples. It fails for review if arguments are already enabled in a changed Debian configure recipe. Repository availability and upstream support lifecycles are separate concerns.

The Ubuntu finding applies to the cited package, not automatically every Ubuntu release, derivative, PPA or locally rebuilt binary. The Alpine master recipe is not a verification of every stable branch. FreeBSD Ports options may be changed locally or by a package builder; inspect the installed package's options rather than assuming every binary uses the defaults.

A candidate row adds no CLI target, build recipe or compatibility guarantee. FreeBSD requires native BSD build/install/service validation. Existing Debian or SLES packages must not be installed on another distribution or architecture; our amd64 outputs are not ARM packages for a Raspberry Pi.

Evidence sources

  • [D] Debian: inspected 4.1.3-1 build rules omit --enable-command-args. Recorded Debian 11–14 source/custom versions and actual project build/install/TLS evidence are in the linked release history. The Debian transformation makes the narrow option insertion and rejects an already-enabled recipe.
  • [S] SLES: the pinned OBS source manifest identifies NRPE 4.1.1 at revision 835292739a5736a9d8f0460f670b6f15. The native build guide describes the actual policy changes; the operator field note separates the old server, client/server package confusion, firewall and plugin problems.
  • [F] FreeBSD: the official port Makefile identifies version 4.2.0 and an off-by-default ARGS option. The follow-up records why Ports-generated --disable-command-args cannot be assumed to leave the compiled macro disabled in the reviewed upstream configure block.
  • [U] Ubuntu: the official 4.1.3-1ubuntu1 acceptance record explicitly records Ubuntu's addition of --enable-command-args and the retained disabled runtime default. The record is dated 20 December 2024.
  • [A] Alpine: the official APKBUILD identifies 4.1.3-r0 and passes --enable-command-args to configure.

  • [R] Arch: the official FS#66574 report identifies version 4.0.2 and the maintainer's May 2020 decision. It provides historical evidence, not an independently checked current package.

  • [P] Runtime/source follow-up: 30 October 2026 review and machine-readable identities/results. Five container probes passed; Arch's current AUR evidence is source-only.

Classify a real installation

  1. Record OS/release/architecture, package name/version, repository origin and the daemon executable's version/owner. Distinguish nrpe from check_nrpe. The read-only diagnostic can help inventory an existing Linux host.
  2. Inspect the exact package's build recipe/options for compiled argument support. A generic comment in nrpe.cfg or a version number alone is not evidence.
  3. Review the main configuration and includes for the intended runtime argument policy. Keep arguments disabled when fixed commands meet the requirement.
  4. On an isolated target, verify an actual permitted argument-bearing request over the intended TLS connection and compare it with the local plugin result. A rejected request can also result from runtime policy, access or bad command definitions; a timeout or TLS failure does not prove a missing build option.
  5. Before adding a new supported target, implement matching native packaging, source/license export, fresh installation and protocol tests, then the separate host lifecycle checks.

Keep the matrix current

During the maintenance review, record the review date, exact package/repository and recipe revision or immutable version, source link, relevant configure options and evidence type. Keep source inspection, container protocol results and real-host outcomes distinct. Recheck moving branches before acting on their entries and update changed findings rather than silently extending them to all releases of a distribution.
