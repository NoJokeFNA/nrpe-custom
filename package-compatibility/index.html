NRPE package compatibility matrix

Source f3ccf8f

Reviewed: 30 October 2026. The assessment answers whether a custom build is needed because the installed NRPE package lacks required command-argument or TLS/SSL support. It applies to the listed package and requirement, not every installation of that OS.

For exact tested versions, argument settings, TLS checks and source/binary inspection, open Test results — 30 October 2026. That report is also available as Test results in the documentation navigation. This page summarizes the patch decision; the report keeps the technical evidence.

Assessment: Yes means a custom build is needed for the stated requirement; No means the reviewed regular package already provides it; Unconfirmed means the evidence is insufficient. Debian's Yes applies only when remote arguments are needed. SLES's Yes refers to replacing the cited legacy 2.15 server, not every SLES installation or an unconditional requirement for this tool: a compatible maintained regular package can also replace it. The tool does not patch firewall rules, missing plugins or TLS configuration.

Version selection

New reviews compare the latest stable upstream release with the newest candidate from each OS release's refreshed native repositories. The test results record the current 4.2.0 upstream check and distribution versions separately. Previous versions remain dated evidence, not pins for the next review.

For Debian, recorded versions come from the published package evidence. The builder discovers the actual source from the selected suite; this matrix does not pin a future build to those examples. It fails for review if arguments are already enabled in a changed Debian configure recipe. Repository availability and upstream support lifecycles are separate concerns.

The Ubuntu finding applies to the cited package, not automatically every Ubuntu release, derivative, PPA or locally rebuilt binary. The Alpine master recipe is not a verification of every stable branch. FreeBSD Ports options may be changed locally or by a package builder; inspect the installed package's options rather than assuming every binary uses the defaults.

Other distributions/repositories Not reviewed by this matrix Review their current recipe and installed package; absence from this page means unknown, not affected or unaffected

The separate optional Arch target is implemented and passed native container packaging/install/TLS/rejection checks. It changes the historical security policy deliberately, is excluded from all, and does not establish the behavior or security of an AUR-installed binary.

A disabled feature can be an intentional security restriction. Its absence alone is not a packaging defect or a recommendation to enable it. This tool enables argument support when explicitly needed; it does not fix the cited vulnerabilities by enabling that support. Prefer fixed commands when arguments are unnecessary.

A candidate row adds no CLI target, build recipe or compatibility guarantee. FreeBSD requires native BSD build/install/service validation. Existing Debian or SLES packages must not be installed on another distribution or architecture; our amd64 outputs are not ARM packages for a Raspberry Pi.

TLS and patch necessity

A TLS failure alone is not a reason to apply this tool's patch. First check TCP reachability, matching TLS settings, trusted certificates, permissions and the actual daemon version using Verify TLS & identity. A custom build or newer server can be necessary when the installed binary cannot provide the required TLS/SSL support. This tool enables compiled arguments on Debian and provides a native newer server for the cited legacy SLES case; its current changes are not a general fix for every TLS failure.

The dated TLS follow-up records successful certificate-authenticated TLS 1.2 tests for the five container-tested regular packages above. Their assessment remains No for the tested argument and TLS requirements. A passing TLS test adds no need for a custom build; a failed handshake remains unconfirmed until its cause is established. Certificate-policy changes need configuration, not automatically a rebuilt binary.

Evidence sources

  • D Debian: inspected 4.1.3-1 build rules omit --enable-command-args. Recorded Debian 11–14 source/custom versions and actual project build/install/TLS evidence are in the linked release history. The Debian transformation makes the narrow option insertion and rejects an already-enabled recipe.
  • S SLES: the pinned OBS source manifest identifies NRPE 4.1.1 at revision 835292739a5736a9d8f0460f670b6f15. The native build guide describes the actual policy changes; the operator field note separates the old server, client/server package confusion, firewall and plugin problems.
  • F FreeBSD: the official port and the exact official binary were inspected. The report explains why ARGS=off does not describe the compiled behavior of that binary. Native runtime and TLS checks remain open.
  • U Ubuntu: the official 4.1.3-1ubuntu1 acceptance record explicitly records Ubuntu's addition of --enable-command-args and the retained disabled runtime default. The record is dated 20 December 2024.
  • A Alpine: the official APKBUILD identifies 4.1.3-r0 and passes --enable-command-args to configure.

  • R Arch: the official FS#66574 report identifies NRPE 4.0.2 and the May 2020 refusal to restore the feature, explicitly citing AVG-587. The 2018 advisory records disabling argument support as the security measure. This establishes the historical official-package decision, not the intent of today's AUR maintainer or a current-version vulnerability assessment.

  • P Runtime/source follow-up: 30 October 2026 review and machine-readable identities/results. Five container probes passed; Arch's current AUR evidence is source-only.

Classify a real installation

  1. Record OS/release/architecture, package name/version, repository origin and the daemon executable's version/owner. Distinguish nrpe from check_nrpe. The read-only diagnostic can help inventory an existing Linux host.
  2. Inspect the exact package's build recipe/options for compiled argument support. A generic comment in nrpe.cfg or a version number alone is not evidence.
  3. Review the main configuration and includes for the intended runtime argument policy. Keep arguments disabled when fixed commands meet the requirement.
  4. On an isolated target, verify an actual permitted argument-bearing request over the intended TLS connection and compare it with the local plugin result. A rejected request can also result from runtime policy, access or bad command definitions; a timeout or TLS failure does not prove a missing build option.
  5. Before adding a new supported target, implement matching native packaging, source/license export, fresh installation and protocol tests, then the separate host lifecycle checks.

Keep the matrix current

During the maintenance review, record the review date, exact package/repository and recipe revision or immutable version, source link, relevant configure options and evidence type. Keep source inspection, container protocol results and real-host outcomes distinct. Recheck moving branches before acting on their entries and update changed findings rather than silently extending them to all releases of a distribution.
