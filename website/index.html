Documentation website and GitHub Pages

The website is static HTML/CSS/JavaScript with no analytics, remote fonts, submission database or hosted backend. Existing Markdown remains the source of documentation. The builder rewrites internal links, creates a local search index and checks every generated internal link/anchor. Original third-party notices are copied without changing their text.

Presentation and field notes live under website/. English matches the project documentation. The initial SLES note uses only reported observations, not an invented testimonial or production TLS claim. New reports follow the field-note guide.

Homepage content and CLI capture

The homepage links to GitHub's latest release rather than hardcoding a release version. Its supported-target table is derived from the README table, keeping target names and package formats in one source. The project story summarizes the reported troubleshooting; it does not claim a successful production upgrade.

website/assets/cli-help.png shows actual python3 nrpe.py --help output captured from application revision 8a2b3d33c0fa. It is a static terminal view, not a live session or a successful build result. Refresh it when the command list changes: capture that command's output, render it as plain escaped text in a local terminal-style browser view, and take a screenshot. Keep machine names, paths and private infrastructure out of the capture. No screenshot tooling is required to build or use the website.

Local preview

Use Python 3.9+ and an isolated environment; the NRPE CLI does not need the website dependency:

python3 -m venv .nrpe/site-venv
.nrpe/site-venv/bin/python -m pip install -r requirements-website.txt
.nrpe/site-venv/bin/python website/build.py
python3 -m http.server 8000 --directory .nrpe/site

Open http://localhost:8000/nrpe-custom/. On Windows use .nrpe\site-venv\Scripts\python.exe for environment-local Python commands. The production base path is /nrpe-custom; builds for another path cannot be published by the guarded publisher. Rebuilds replace only a directory carrying this builder's manifest; arbitrary directories, unknown added files and the workflow-state root are refused. In-checkout output belongs under .nrpe/site/<name>, not .nrpe itself.

The website workflow tests rendering, links and publication guards and uploads a preview artifact. It never commits or publishes automatically, preserving human-only Git authorship.

Reviewed publication to gh-pages

Work on a topic branch, review and integrate into develop. Publication requires a separate explicit maintainer request. From the exact clean develop or master commit that should be shown on the website:

.nrpe/site-venv/bin/python website/build.py
.nrpe/site-venv/bin/python website/publish.py
.nrpe/site-venv/bin/python website/publish.py --push

The default is a read-only preview. --push checks source identity, base path, all asset hashes and the human author/committer. A separate temporary Git index creates a commit containing only the generated website, without replacing the source checkout/index. Deployment history is appended on gh-pages with an ordinary fast-forward push, never force-pushed. Concurrent changes are rejected. Master/develop are not deployment targets and must never be deleted. Do not develop features directly on gh-pages or edit generated HTML by hand.

The site does not update itself after a master push. Rebuild and explicitly publish a reviewed commit when docs change; automatic package releases remain a separate workflow.

GitHub Pages setup by the repository owner

The requested hosting source is gh-pages, repository root. In GitHub:

  1. Open Settings → Pages.
  2. Select Deploy from a branch.
  3. Select gh-pages, / (root), then save.
  4. Wait for deployment and verify the homepage, FAQ and a deep link.

The expected URL is https://nojokefna.github.io/nrpe-custom/. The repository visibility is managed by the owner and is not changed by the publisher. Pages availability and site visibility depend on GitHub's plan and settings. Review content for public disclosure; never include private logs, actual infrastructure addresses or keys.

If the connected integration cannot access the Pages settings API, the owner must complete setup in Settings. A pushed branch alone does not prove the website is live. Deployment and HTTP/browser checks must complete before claiming successful hosting. See GitHub Pages setup.
