Installation & services

Does a separate NRPE agent also need Nagios Core locally?#

No. Nagios Core schedules checks on the monitoring server. Its check_nrpe client contacts the NRPE daemon on the monitored host, which executes the configured local plugins. A host used only as an NRPE agent needs its NRPE daemon and required plugins, but does not need a local Nagios scheduler. Starting Nagios alone does not start a separately packaged NRPE daemon.

The two-service command applies to the combined server, not every NRPE agent. See the connection map for the separate roles.

TLS & certificates

NRPE checks on SLES: services first, then SSL/TLS#

Check the managed NRPE service first. On a combined Nagios/NRPE server, both services must run. If the connection still fails, compare the client and daemon versions and their TLS configuration before considering a custom build.

These questions belong to the same troubleshooting sequence. The operator later clarified that starting the missing nrpe.service resolved the checks in their combined Nagios/NRPE setup. A custom package was not needed for that service availability problem.

Start with the intended service and listening process, then investigate TLS only if the connection still fails. A stopped daemon cannot itself negotiate TLS; an SSL-handshake message from an NRPE process shows that a process was running at that time. Historical logs, a manually started daemon and the current systemd state can describe different moments or different listeners.

Which services must run on a combined Nagios and NRPE server?

When Nagios Core and the NRPE daemon are installed on the same SLES server, and the installed units are named nagios.service and nrpe.service, enable and start each service:

sudo systemctl enable --now nagios.service
sudo systemctl enable --now nrpe.service
systemctl is-active nagios.service nrpe.service

enable --now configures startup at boot and starts the service immediately. Both should report active for this combined setup. Nagios schedules checks; NRPE independently listens for and executes remote plugin requests. If a unit is missing or fails, inspect the installed unit names and logs before replacing packages:

systemctl list-unit-files nagios.service nrpe.service
sudo systemctl status nagios.service nrpe.service --no-pager
sudo journalctl -u nagios.service -u nrpe.service -n 100 --no-pager

Package-provided service names vary. For the custom Debian server package in this project, the NRPE unit is nagios-nrpe-server.service:

sudo systemctl enable --now nagios-nrpe-server.service

Follow the official Nagios Core documentation and NRPE documentation for complete installation and deployment configuration. Enabling a service does not install missing plugins, provision TLS credentials or configure monitoring checks.

Before interpreting an SSL error, also confirm which process owns port 5666:

sudo ss -ltnp 'sport = :5666'

If a manual test daemon still owns the port, an enabled systemd unit alone does not prove it is serving requests. Restore the intended managed instance before retrying the same check from the monitoring server. For a persistent failure, continue with the version/TLS checks below.

Why does the old SLES 12 NRPE daemon fail its SSL handshake?

If the managed daemon is active and requests still fail, compare versions and TLS policy. The original reported server ran NRPE 2.15-4.24, linked to OpenSSL's 1.0 ABI. That old NRPE advertises anonymous DH, not modern certificate authentication. A newer NRPE/client built for SLES 12 can use certificate-authenticated TLS 1.2 with the original OpenSSL 1.0.2 library. TLS 1.3 requires a newer TLS library and is not provided by this build. disable_syslog=0 is unknown to the old daemon; commenting it out removes the warning but does not fix TLS compatibility.

Check the server package, not just the client version. Installing monitoring-plugins-nrpe updates check_nrpe; it does not replace the daemon provided by nrpe. The operator's later installation attempt still showed server 2.15 after installing client 4.1.1. Follow the server-package identity and installation checks and SLES deployment checklist.

The message Could not complete SSL handshake. 1 alone does not identify a specific cipher, certificate or trust failure. Compare the actual server/client versions, command, TLS settings and simultaneous logs. Do not disable encryption or certificate verification to hide the error. Build-time --ca-cert affects source downloads, not the deployed NRPE certificate configuration.

To isolate this on SLES 12 SP3 before upgrading, the temporary plaintext diagnostic documents the user's successful NRPE 2.15 / check_nrpe 4.1.0 test on a separate port. It includes anonymized examples, the encountered errors and cleanup; it does not recommend disabling TLS in production.

For NRPE 4.1.1 on SLES 12, also review the complete authenticated DHE-RSA policy. With this old OpenSSL integration, ssl_use_adh=0 skips DH initialization and can produce no shared cipher with modern clients. Use the complete documented policy, which explicitly excludes anonymous ciphers, rather than enabling ADH alone. It was tested against OpenSSL 3.5.7 with certificate verification intact.

Versions & builds

Which SLES version does this project target?#

SLES 12 SP3, confirmed by /etc/os-release. The active target is sles12sp3; see the native build guide.

When do I actually need a custom build?#

Use the distribution package when it already provides the required feature. The package compatibility matrix records inspected versions, sources and review dates, including confirmed cases and open candidates. It distinguishes package build options from this tool's supported targets.

A custom build makes sense when a required compiled feature is missing. Before rebuilding, distinguish service/configuration problems from missing features:

  1. Check that the intended NRPE service is running and inspect its logs.
  2. Confirm the monitoring server can reach NRPE with the intended allowed hosts, firewall rules and TLS configuration.
  3. Confirm that the configured plugin exists and runs as the NRPE service user.
  4. If arguments are required, check both the package's compiled support and the runtime policy. dont_blame_nrpe=0 intentionally rejects arguments even when support was compiled in. Enable arguments only after reviewing the command definitions and validating permitted inputs.

A stopped service or an argument-disabled runtime setting alone is not a reason to compile another binary. This project's Debian build is for deployments that deliberately need compiled command-argument support; it preserves disabled runtime arguments by default and disabled Bash command substitution.

After changing configuration, restart the applicable NRPE service and repeat the actual remote check. enable --now does not restart an already active service to reload modified configuration. See installation and deployment security for this project's custom package scope.
