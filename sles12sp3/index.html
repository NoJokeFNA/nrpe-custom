SLES 12 SP3 RPM target

Source 0895e58

The affected deployment is SLES 12 SP3, confirmed by /etc/os-release on 2026-10-28. Its original package is NRPE 2.15-4.24, linked to libssl.so.1.0.0 and libcrypto.so.1.0.0. The target is sles12sp3.

python3 nrpe.py verify sles12sp3
python3 nrpe.py test sles12sp3

Use --rebuild to deliberately replace existing local outputs. Use only matching SLES 12 SP3 RPMs in this target's output directory.

Build architecture and matching inputs

The native build and runtime stages use SUSE's genuine image, pinned to:

registry.suse.com/suse/sles12sp3@sha256:0995dbf051274a3a5baf19c7f94ce7ebe69d7aa91f7b3b22248bd06d7122e53a

Its identity is ID=sles, VERSION_ID=12.3, x86_64, with RPM 4.11.2 and OpenSSL 1.0.2j. SLES_BASE_IMAGE can select an approved equivalent, but the native guard rejects other distributions/releases and requires the OpenSSL 1.0 ABI. The runtime image contains no compiler or preinstalled NRPE server.

The historical image has no configured repositories and the old SP3 backports index is empty. Instead, the bootstrap manifest pins original SLE-12 GA/SP3 Server and SDK RPMs available through SUSE's public OBS API. Each entry records its original URL, size, SHA-256, name, version, architecture, vendor and SUSE signing key.

A separate Python download stage fetches and hash-checks those RPMs and the pinned OBS sources. A company CA is added only to that process's TLS context; it is not copied into target packages. The actual SLES stage independently checks the pinned RPM hashes, required SUSE signatures and package identities before installing anything. Downloads are not treated as signature verification. Native installation uses the complete local dependency set, retaining normal RPM dependency checks; no registration credentials or license terms are supplied or accepted by this workflow. No system OpenSSL replacement is required.

Python is not needed in the old target image. NRPE and its support packages are compiled/packaged by SLES 12's own tools. An ISO is not required by this workflow.

Sources and package identities

  • NRPE: reviewed immutable OBS revision 835292739a5736a9d8f0460f670b6f15, version 4.1.1, local Release 0.withargs1. Command arguments remain compiled in, runtime-disabled by default; Bash command substitution stays disabled. This is a native rebuild, not a reproduction of the old installed NRPE 2.15 package.
  • Nagios build macros: immutable OBS revision a911087cc73b87e04465861110d43754, version 0.14-0, built natively. The upstream spec explicitly supports SLES 12. This build dependency is not faked or supplied by an incompatible binary.
  • Nagios user package: pinned original system-user-nagios 1.0.0-0, built natively after the macros. Existing users and groups are handled by the original package scripts.

output/sles12sp3/ contains the server, matching monitoring-plugins-nrpe client, real user-package RPM, all three source RPMs, four input manifests, original OBS files including history, and SHA256SUMS for all three binary RPMs. The macros' build-only binary is not a runtime dependency or release asset. Its corresponding source and BSD notice are included for rebuilding the workflow.

The source/license gate checks every original input and SRPM member, the client/server source/version relationship, the bootstrap manifest and component notices. See license evidence and the notice directory.

TLS and the original handshake failure

The operator later clarified that starting the missing nrpe.service restored the checks in their combined Nagios/NRPE setup. Check the services-first FAQ before replacing packages. That service-state fix did not require a custom build and is separate from the old binary's certificate-authentication limitations.

For the user-performed pre-upgrade diagnostic with NRPE 2.15 and check_nrpe 4.1.0, see isolating an NRPE TLS handshake failure. It documents a separate temporary plaintext instance, the successful result and cleanup using anonymized hosts and documentation addresses, without modifying the production service or reloading systemd.

NRPE 2.15 uses legacy anonymous DH. Merely enabling services or adding modern configuration directives does not add certificate support to that old binary. This build supplies NRPE 4.1.1 and a matching client against the existing OpenSSL 1.0 ABI. The integration test explicitly requires TLS 1.2, excludes anonymous authentication, requires a client certificate and checks rejected/enabled command arguments. It does not weaken cipher settings or disable certificate verification to make the test pass. TLS 1.3 is not supported by OpenSSL 1.0.2 and is not claimed.

For the deployed server, back up the old package/configuration, review included files and configure compatible CA/server/client certificates on both ends. Build-time --ca-cert does not provision production NRPE TLS. The FAQ distinguishes service startup from TLS compatibility. Use the SLES-specific DHE-RSA configuration: NRPE 4.1.1 needs DH initialization enabled together with an explicit cipher list that excludes anonymous authentication. The modern-client test passed with OpenSSL 3.5.7, verified server hostname/chain and a separate required client certificate; a connection without that client certificate was rejected.

Recorded validation and limits

The target is published; see the release history for exact master-commit, CI and independently checked release-asset evidence. Earlier local migration runs are retained in that history. A fresh clean-checkout run is required for every release candidate; historical results do not replace it.

Container tests run NRPE directly. They do not validate real-server systemd, reboot, site-specific commands, production certificates, update or rollback. Use installation, rollback and practical validation before deployment.

The SUSE lifecycle lists SLES 12 SP3 general support end as 2019-06-30 and LTSS end as 2022-06-30. This is a requested legacy compatibility build, not extended vendor maintenance or certification. Historical package/image availability can change and does not guarantee security support.
