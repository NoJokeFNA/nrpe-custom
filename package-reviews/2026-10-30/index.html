Distribution NRPE package review: 30 October 2026

Source 7258261

This follow-up replaces broad OS-family assumptions with installed-package observations. Five regular Linux package installations were tested sequentially in disposable x86_64 containers. No custom project package was installed in these probes, no host package was installed and no container port was published.

Runtime observations

Actual OS Installed server/client packages Policy 0 Policy 1 Compile-option change needed for these arguments?
Ubuntu 22.04 nagios-nrpe-server / nagios-nrpe-plugin 4.0.3-1ubuntu2 Rejected Exact ALPHA/BETA response No
Ubuntu 24.04 nagios-nrpe-server / nagios-nrpe-plugin 4.1.0-1ubuntu3 Rejected Exact ALPHA/BETA response No
Alpine 3.22.7 nrpe / nrpe-plugin 4.1.1-r0 Rejected Exact ALPHA/BETA response No
Fedora 43 nrpe / nagios-plugins-nrpe 4.1.3-4.fc43 Rejected Exact ALPHA/BETA response No
AlmaLinux 9.8 with EPEL 9 nrpe / nagios-plugins-nrpe 4.1.2-2.el9 Rejected Exact ALPHA/BETA response No

Both policies first passed a fixed-command baseline returning NRPE_BASELINE_OK. The argument-disabled requests returned exit 3 with a header underflow message; the deliberately enabled requests returned exit 0 and exactly NRPE_ARG_PROBE:ALPHA:BETA. This shows why header underflow alone is not a unique TLS diagnosis. The controlled probe used plaintext consistently on both ends.

These versions and repositories are observations of the tested transaction, not a claim about every release, architecture or third-party rebuild. EPEL 9 on AlmaLinux does not establish an actual RHEL, Rocky or Oracle Linux host result. Alpine's stable-branch package also differs from the previously reviewed master recipe; preserve that distinction in the matrix.

Procedure and integrity boundary

  1. Start an official matching base image with no published port and a read-only mount of the reviewed helper. Keep the configured proxy and mount its public CA bundle separately where HTTPS tools require it.
  2. Install the distribution's regular NRPE daemon and client through normal APT, APK or DNF repositories. Ubuntu used its matching Universe packages; Alpine used matching v3.22 repositories; Fedora used matching Fedora repos; AlmaLinux first installed its regular EPEL repository package, then EPEL 9 NRPE. Package authenticity/dependency checks were not disabled.
  3. Record OS, exact installed versions, package origin/source where exposed, daemon/client versions and SHA-256 hashes. The machine-readable record retains image identities and these observed binary hashes. Binary hashes are not package archive signatures.
  4. Use a real package-provided service account and temporary configuration, with a foreground daemon bound only to 127.0.0.1:15666. Disable Bash command substitution. Test a fixed /bin/echo baseline before each policy, then a command with the controlled $ARG1$ / $ARG2$ pair.
  5. Stop only the probe's daemon, remove its temporary files and discard the container. The reusable protocol helper and its requirements document the equivalent check without installing packages or changing packaged configuration.

The base image digest is recorded, but package repositories were live and not snapshotted. This is dated evidence, not a bit-for-bit reproducible build. The initial plaintext probe establishes no TLS or certificate policy, systemd/OpenRC startup, reboot, production-plugin behavior, update or rollback guarantee. None of the reviewed systems becomes a supported custom-build target through this test.

TLS follow-up

The regular packages were also checked over certificate-authenticated TLS 1.2 in fresh disposable containers. This is a separate round from the original plaintext observation, using the helper's NRPE_PROBE_TRANSPORT=tls mode. All five regular-package pairs in the table above passed: Ubuntu 22.04, Ubuntu 24.04, Alpine 3.22.7, Fedora 43 and AlmaLinux 9.8 with EPEL 9. Their recorded NRPE executable hashes match the earlier plaintext round. No tool patch was needed for the tested arguments or certificate-authenticated TLS connection.

The trusted baseline and exact argument response must pass, arguments must be rejected with runtime policy 0, and both a wrong server CA and a missing client certificate must be rejected. A final trusted baseline verifies that the daemon still responds after those negative controls. All traffic remains on IPv4 loopback; there are no published ports or production configuration changes.

The test uses short-lived, local test certificates with authenticated RSA cipher suites and excludes anonymous/null ciphers. Ubuntu 22.04, Ubuntu 24.04 and Fedora 43 passed with DHE-RSA-AES256-GCM-SHA384. Alpine 3.22.7 initially reported no shared cipher with that DHE-only configuration. Adding ECDHE-RSA-AES256-GCM-SHA384 to the allowed list made the same unmodified Alpine binaries pass all controls. This was a cipher-configuration problem, not evidence that the argument patch was required to repair TLS. A temporary Alpine repository index fetch failure was retried with normal TLS and package checks retained.

AlmaLinux's first package-install attempt encountered truncated repository metadata from a selected mirror and was stopped before the protocol probe. The successful retry used the official AlmaLinux repository server plus official EPEL 9, keeping HTTPS verification, RPM signatures and matching-release dependencies.

The machine-readable record retains the completed TLS outcomes and binary identities. These local checks do not establish hostname verification, production certificate roles/revocation, TLS 1.3, remote Nagios client compatibility, service startup, reboot or upgrade/rollback behavior. An absent TLS result in a source-only row remains untested, not a confirmed TLS defect or patch need.

Arch: current repository absence and AUR source review

The archlinux:base image identified itself as 20261025.0.616225. The initial package refresh encountered proxy-CA trust errors. Using the mounted CA explicitly in pacman's curl downloader corrected HTTPS verification without disabling it. The successfully retrieved core/extra repository metadata then reported target not found: nrpe. No Arch package installation or protocol pass is claimed. This is an observation of those repositories and architecture, not proof that NRPE is unavailable from every Arch package source.

The public AUR metadata identifies nrpe 4.1.2-1. The inspected PKGBUILD does not pass a command-argument configure option. The exact upstream 4.1.2 configure source only defines ENABLE_COMMAND_ARGUMENTS when the option is supplied. This is a current source-level candidate for an argument-enabled rebuild. No AUR build code was executed, and no AUR binary was installed. Its recipe SHA-256 is recorded in the JSON evidence. The old Arch issue remains historical context, not today's runtime result.

FreeBSD: why the first classification needed correction

The NRPE 4.2.0 port defines ARGS but does not enable it by default. That declaration alone is not proof that a built binary lacks arguments. The Ports options helper turns a disabled ARGS_CONFIGURE_ENABLE=command-args into --disable-command-args. However, the reviewed upstream 4.2.0 generated configure block checks whether the option was provided, then defines the macro without testing whether its value is yes or no.

An isolated execution of that exact, small configure block from upstream commit cf47f059637fe4ad23dd4a5f2612e2787ce7c09d produced:

Configure-option state ENABLE_COMMAND_ARGUMENTS defined
Omitted No
Supplied with value no (disable) Yes
Supplied with value yes (enable) Yes

This validates the configure-fragment behavior, not an actual FreeBSD package or service. A native package-options, generated-header and protocol check is still required. The matrix therefore no longer treats FreeBSD as a confirmed argument-disabled binary or a confirmed need for our patch. No upstream bug report or new security advisory is claimed by this observation.

Next checks

  • Build and exercise the reviewed Arch AUR recipe and an explicitly argument-enabled revision in a disposable native environment before claiming runtime compatibility. Preserve source integrity and real package versioning.
  • Inspect a native FreeBSD binary/generated header and run both argument policies. No BSD VM or access was available here; Linux containers cannot establish it.
  • Recheck a specific package version before applying these findings to a new release or derivative. Prioritize an actual missing feature over adding targets whose regular packages already provide the needed capability.
