Installing a custom NRPE package

Source 686f2f3

Run these commands on the destination Linux server. Python, Docker, and this checkout are needed on the build workstation, not on the destination server. Use a package built for the destination's distribution release and architecture. The current SLES target is SLES 12 SP3 x86_64, not every SLES 15 service pack.

For the complete NRPE server/client and Nagios setup, use the official NRPE documentation and Nagios Core documentation. This guide covers deployment of the custom packages and essential configuration checks; it does not replace those manuals or distribution-specific plugin and TLS instructions.

Prepare the files

Build and test the selected target on the workstation with, for example, python3 nrpe.py verify debian12 or python3 nrpe.py verify sles12sp3. Copy the following files into a dedicated directory on the destination server:

Destination Build output directory Files to copy
Debian 11 output/debian11/ nagios-nrpe-server_*_amd64.deb, SHA256SUMS
Debian 12 output/debian12/ nagios-nrpe-server_*_amd64.deb, SHA256SUMS
Debian 13 output/debian13/ nagios-nrpe-server_*_amd64.deb, SHA256SUMS
Debian 14 output/debian14/ nagios-nrpe-server_*_amd64.deb, SHA256SUMS
SLES 12 SP3 output/sles12sp3/ nrpe-*.x86_64.rpm, system-user-nagios-*.noarch.rpm, monitoring-plugins-nrpe-*.x86_64.rpm, SHA256SUMS

Keep exactly one server package version in that directory so the wildcards below select the intended package. Source RPMs, manifests, and Debian build information are useful provenance but are not installed on the destination.

Change into the directory containing the copied files and verify them:

sha256sum --check SHA256SUMS

Continue only if every entry reports OK. Copy the checksum file through a trusted channel alongside the packages; checksums detect changes but do not authenticate the publisher by themselves. Keep all three SLES binary RPMs available for this check even if the destination already has the user package installed. For releases that include SHA256SUMS.sig, first perform the release authentication check using an independently trusted maintainer key before extracting/installing packages. Unsigned releases are identified in the release history.

If NRPE is already installed, back up its configuration before updating. Review package-manager prompts about configuration files and dependencies. Preserve the site's command definitions, allowed monitoring hosts, and TLS configuration. Package installation may start or restart a service.

For an existing deployment, follow updates and rollback before replacing packages. The configuration examples and maintenance policy describe optional checks and verification boundaries.

Debian 11, 12, 13, or 14

Check the destination release and architecture:

cat /etc/os-release
dpkg --print-architecture

The architecture must be amd64. Use the package from the matching Debian output directory; a Debian 12 package is not a package for every Debian release.

From the directory with the verified .deb file:

sudo apt update
sudo apt install ./nagios-nrpe-server_*_amd64.deb
dpkg-query -W -f='${Package} ${Version} ${Architecture}\n' nagios-nrpe-server

APT resolves runtime dependencies through the destination's configured Debian repositories. The explicit ./ selects the local custom package. Confirm that the installed version contains +withargs1 (or the custom revision of the build you selected); the upstream version itself is discovered at build time.

Edit /etc/nagios/nrpe.cfg using your preferred editor. Review the configuration steps below before restarting.

sudo systemctl enable nagios-nrpe-server
sudo systemctl restart nagios-nrpe-server
sudo systemctl status nagios-nrpe-server --no-pager

If startup fails, inspect the service log:

sudo journalctl -u nagios-nrpe-server -n 100 --no-pager

SLES 12 SP3

Check the destination release and architecture:

cat /etc/os-release
uname -m

Expect SLES 12.3 and x86_64. The current pinned build produces:

nrpe-4.1.1-0.withargs1.x86_64.rpm
system-user-nagios-1.0.0-0.noarch.rpm

The destination must actually be SLES 12.3 x86_64. Do not install a SLE-15 package or replace the system OpenSSL. Retain the old NRPE 2.15 package and back up the main configuration, includes, plugins and TLS files before upgrading. The newer package retains /etc/nrpe.cfg as a configuration file; review package prompts and any .rpmnew/.rpmsave files rather than assuming that defaults replace an existing deployment's policy.

Use your authorized matching SLES-12 repositories for missing runtime dependencies. Review the package requirements and user package first:

rpm -qp --requires ./nrpe-4.1.1-0.withargs1.x86_64.rpm
rpm -q system-user-nagios

The minimal test image additionally needs original libwrap0 and util-linux-systemd; a full server may already provide them. Resolve missing prerequisites using the destination's matching repositories, for example:

sudo zypper refresh
sudo zypper install libwrap0 util-linux-systemd shadow netcfg grep sed coreutils

Then install the verified local artifacts with normal RPM dependency and payload checks. If no suitable user package exists, install the companion and server in one transaction:

sudo rpm --upgrade --verbose --hash \
  ./system-user-nagios-1.0.0-0.noarch.rpm \
  ./nrpe-4.1.1-0.withargs1.x86_64.rpm

If a suitable user package is already installed, keep it and install the server:

sudo rpm --upgrade --verbose --hash ./nrpe-4.1.1-0.withargs1.x86_64.rpm

These are locally built unsigned RPMs. Verify their hashes through a trusted channel (or the optional release signature when enabled) before installation. Never use --nodeps, --nosignature or global repository signature bypasses. This project's test does not bypass missing dependencies. SLES 12's zypper does not provide the newer --allow-unsigned-rpm option used in some SLE-15 examples.

The matching client RPM is available for a SLES 12 SP3 monitoring host:

sudo rpm --upgrade --verbose --hash ./monitoring-plugins-nrpe-4.1.1-0.withargs1.x86_64.rpm

It needs the same real Nagios user and matching runtime libraries. Do not install that client RPM on another distribution; use its native client package instead. All three binary files are needed to check the unchanged SHA256SUMS, even when only the server/user package will be installed on the monitored host.

Confirm the installed server and user:

rpm -q nrpe
getent passwd nagios

Expect nrpe-4.1.1-0.withargs1.x86_64 for the current build. zypper install nrpe without the local filename can select the repository package instead of this custom build.

Edit /etc/nrpe.cfg using your preferred editor. Review the configuration below before restarting:

sudo systemctl enable nrpe
sudo systemctl restart nrpe
sudo systemctl status nrpe --no-pager

If startup fails:

sudo journalctl -u nrpe -n 100 --no-pager

Configure and start NRPE

Distribution Configuration Service
Debian /etc/nagios/nrpe.cfg nagios-nrpe-server
SLES 12 SP3 / OBS recipe /etc/nrpe.cfg nrpe

Argument support is compiled in, but dont_blame_nrpe=0 remains the packaged default. Keep it at 0 if the monitoring server should not supply arguments. To deliberately enable them, edit the existing settings in the appropriate configuration file, for example:

allowed_hosts=127.0.0.1,::1,192.0.2.10
dont_blame_nrpe=1

Replace 192.0.2.10 with the actual monitoring server address. Define permitted commands and validate any $ARG1$, $ARG2$, etc. they accept. Configure production TLS authentication and allow incoming TCP 5666 (or your chosen server_port) only from the intended monitoring servers. Keep Bash command substitution disabled. See deployment security and network requirements.

Restart the distribution's service after changing its configuration, using the commands above. A successful service start does not prove argument handling or remote connectivity; exercise the configured check from the real monitoring server with the intended TLS settings and arguments. The project's container tests do not validate the destination's systemd, firewall, or production TLS.

The build-time --ca-cert option configures repository HTTPS trust inside build and test containers. Its CA is not embedded in the exported package and does not provision the destination's NRPE certificates, keys, or operating-system trust.

Review future package-manager upgrades: a repository package can supersede a local custom version. After upgrades, confirm the installed custom revision again and rebuild from reviewed sources when security updates are needed.
